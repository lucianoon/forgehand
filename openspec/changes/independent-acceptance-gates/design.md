## Context

Operator build profiles already pin images/commands and architecture policies before planning. Candidate code and its own tests run in disposable Docker containers. Existing validation does not independently compare business behavior with operator-owned expected results.

## Goals / Non-Goals

Goals: externally owned CLI assertions, explicit criterion coverage, bounded isolated execution, persisted evidence and fail-closed graph/publication gates.

Non-goals: all business rules automatically proven, test oracle generated by the implementing agent, HTTP/browser/stateful testing, benchmark leaderboard, paid model calls, deployment, or cryptographic attestation of a malicious operator/runner.

## Decisions

1. Add optional `acceptance` to BuildProfile, with 1–8 uniquely identified cases. Each binds one exact criterion string to a validated test-phase command and exact expected stdout. Commands must have network=none; each is at most 30 seconds, total timeout at most 120 seconds; output at most 16 KB, expectations at most 8 KB and suite JSON at most 64 KB. Operators must select meaningful observable outputs, not candidate-authored "tests passed" banners.
2. Compare SHA-256 of decoded stdout before sanitization with the operator expectation on the host. Success requires exit 0, complete capture, successful cleanup and exact output (including whitespace). Expected text is not mounted/passed to candidate code. Hashes are evidence identifiers, not a secrecy guarantee. Sanitized stdout remains diagnostic only and cannot determine success.
3. Reuse Docker phase execution with an internally derived single-command profile. Acceptance containers have read-only workspace, no network, existing resource limits and cleanup/quarantine semantics. They cannot alter the checkout that will be published. Each case has independent /tmp; no shared state or services.
4. Profile selection pins suite digest, per-case digest and exact required criteria before planning. An acceptance-enabled profile with uncovered criteria is unsupported. Registry reconstruction detects missing or divergent pinned metadata; old profiles omit the new field when computing fingerprints. Profiles without suites remain compatible, explicitly unverified by this mechanism.
5. Reports record case id/criterion/digest, expected output digest and execution result, with derived success. Graph and publication require complete, matching case identities and criterion coverage; model approval or aggregate success cannot override missing/failed acceptance. Feedback names failures without exposing expected stdout; review summary names the scope and results.
6. Tests independently control runner output, including a fake green test suite with wrong behavior. Real Docker checks use existing digest-pinned Python/Node images and verify wrong outputs, corrected outputs and read-only mounts. No third-party repositories are modified.

## Risks / Trade-offs

- Finite examples can be overfit → no claim of universal correctness; operators own representativeness and add adversarial/regression cases.
- Broad natural-language criteria can be assigned weak cases → exact matching proves declared coverage, not semantic sufficiency. Document human review as mandatory.
- Per-task graph validation checks full acceptance → incremental multi-task plans may need retries until behavior exists; keep this milestone for bounded deliveries.
- Legacy profiles lack suites → compatibility retained but review summaries state no independent acceptance. Administrators must approve/profile-map intended delivery workflows; no global enforcement switch in this milestone.
- Same host and trusted runner → not protection against malicious host operators or a compromised Docker daemon.

## Migration Plan

Additive model fields with defaults; preserve old profile fingerprints. Configure suites outside repositories in existing operator profile configuration and update API/workers together. Existing pinned workflows reject policy drift rather than silently adopt new cases. No automatic service restart, database migration or remote writes.

## Open Questions

Later milestones can add trusted HTTP/browser verifiers, global mandatory-acceptance policy and representative product-level evaluations. None are implied by this CLI gate.
